# R24 renderer and whole-frame hotpath decision audit

Status: **research and independent rebuttal only, 2026-10-29**. No production file was edited, GPU work submitted, browser opened, scene changed, or new measurement performed. Approved audio is outside this audit. Read the R23 historical research draft together with its integration supplement: R23 active-count SourceT layout is now the incumbent, while the over-budget powered candidate remains unadmitted. This document is a roadmap, not a performance or visual acceptance receipt.

## Decision

Keep the current Three.js/WebGL renderer while addressing avoidable CPU reconstruction, complete optical-work admission, and smoke fill independently. Most image formation is already on the GPU. Moving all remaining JavaScript to GPU kernels is neither a complete design nor a demonstrated speedup: it can add transfers, synchronization, sorts, extra passes and stale-state problems without reducing the source–density pair product.

The next concrete deliverable should be a **CPU-only joint-work and sparse-relevance witness**, accompanied by a small exact CPU reuse/prefix-upload change proposed separately. Preserve all physical sources, smoke mass, material profiles, original clocks, current illumination and view identities. Native over-budget GPU runs, asynchronous optical reuse and a renderer migration are separate later admissions.

## Verified implementation and frame graph

`index.html:10` maps `three` to `vendor/three.module.js`; `vendor/three.core.js:6` declares **r180**. `main.js:177` constructs **`THREE.WebGLRenderer`**, with custom render targets providing antialiasing. There is no `WebGPURenderer` scene renderer. Optional HDR presentation can use a separately created WebGPU device; that does not make the scene renderer WebGPU.

The live frame calls physical simulation, celestial/navigation, fireworks and smoke-source flush, photometry/bounds/lighting, dynamic environment, shadow/caustics/sand updates, water captures, then main scene/lens/display. Main and mirror are distinct views. The following is a source audit; entries are not isolated timings.

## Evidence and what it does not establish

`r22-native-powered-mid-frozen-benchmark.json` records126 frame intervals at1209×1292: mean23.919ms, CPU submit23.332ms, GPU18.318ms, about41.47FPS. CPU/GPU overlap; adding them would be wrong. It is one frozen physical phase, not evolving smoke simulation, an isolated kernel timing, or a current R24 benchmark.

R23 native SourceT ABBA reduced the already-admitted870000-pair isolated map/reduce interval from roughly0.739/0.690ms to0.422/0.386ms, with valid output prefixes bitwise equal. This supports actual-count empty-raster removal on that input. The R23 integration supplement explicitly does **not** establish a clean full-frame layout-only speedup or60FPS; HDR calibration drift and workload identity limit that comparison.

The755-packet/1734-row witness needs1309170 SourceT pairs and enters1734 CPU medium queries. Its light field needs1304640 pairs and disables resolved illumination. The independent lifetime witness reaches3986268 resolved pairs for one event, under deliberately different CPU-fixture conditions. It is not a native render reproduction. Earlier smoke proxy rectangles grew from about0.56 to12.55 viewport layers; these are conservative raster upper bounds, not measured executed fragments or a pure SourceT timing.

Older R17/R19 CPU profiles show optical record/bounds/body replay, packing and `getParameter` occupancy plus garbage collection. Those files predate current caches and R22/R23 changes; use them to choose hypotheses, **not** as current percentages. There is no sealed per-component R24 evolving-frame profile. Therefore the priorities below are ranked by known algorithmic cliffs and change scope, not invented current milliseconds.

## CPU/GPU placement and rebuttals

Keep event ordering, IDs/seeds, reserve/commit ledgers, input validation, UI/audio scheduling, contact/lifecycle admission and small host controls on CPU. Their correctness depends on causality and durable observable state, not the number of colored pixels. Share an immutable compiled motor schedule with a GPU evaluator later if useful; do not ask the GPU to supply future poses, reseed per frame or read back an authoritative simulation just to satisfy CPU consumers.

Good GPU candidates are large uniform, independent evaluations whose consumers remain GPU-resident: full current-generation tau/SH batches; packet transport after a coherent buffer/state design; analytic source pose/optical bins consumed directly by raster; conservative visibility/compaction after dataflow proof. A small CPU loop, sort or light solve is not automatically a good compute workload. Worker/SoA CPU optimization can reduce main-thread latency without assuming a backend rewrite, but worker copies, delayed publication and deterministic queue ownership still need a contract.

There is already an **opt-in, default-false exact common-origin whitening cache** in `pyro-smoke-columns.js:231`; the host/API exposes its toggle. It reuses the originally rounded `whiten(eye−mean)` within a density/origin generation, not whole transmission or arbitrary reflected rays. R16's `r16-smoke-column-plan.md` and `r16-smoke-origin-cache-check.{mjs,json}` already cover it:5/5 correctness checks, with varying reflection water-hit origins intentionally bypassing broad cache population. That historical512-endpoint CPU fixture showed **no speed benefit**: scalar off/on medians3.5514/3.8850ms, bounded-as2.6744/2.8691ms despite many hits. Do not reinvent this cache or enable it because its hit count looks good; a later fallback-cost study must revalidate it on the current native workload. These old fixture timings are not a current frame measurement.

**Transfers:** smoke raster currently uploads17 floats ×4096 capacity =278528 bytes per view, plus16384 bytes when the resolved index attribute is present. At755 visible instances the base prefix would be51340 bytes. These are source-level array sizes, not measured PCIe traffic or frame savings; Three r180 uploads the full buffer when no update ranges are supplied. Fireworks already uses active update ranges. Reuse shape/profile packing by immutable density revision, while keeping camera-relative centers and sorted view indices view-specific.

**Sorting/overdraw:** the current smoke blend is order-dependent. Sorting all packets on GPU would require storage buffers/index scatter and still does not remove translucent fill. Weighted OIT, density coalescence, lower-resolution smoke or aggressive tail cutoff change the optical model. A finite support radius has an omitted-tail error; many small tails can sum. A separately certified sparse influence hierarchy may reduce work without deleting physical material, but must bound cumulative tau/T and lit radiance across all consumers. A snapshot-only3D proxy may be rebuilt from authoritative fine state; persistent physical coalescence additionally needs thermal/velocity cross moments and must not be sold as exact density.

**Synchronization:** hot production helpers capture raw GL state (`getParameter`/FBO state) per pass; older profiles show this can matter. MDN notes such getters/status calls may cause round trips. A future explicit owned pass scope could amortize redundant captures, with complete outer state restoration and per-target validation retained; deleting guards is not an optimization proposal. SourceT layout alone does not justify weakening R21/R23 restoration tests. [WebGL best practices](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices#avoid_blocking_api_calls_in_production).

**Readback:** focus picking is a user-triggered1×1 read, hydro diagnostics read the grid only when explicitly requested, screenshots/QA read pixels deliberately. These are not ordinary continuous frame costs. Optional HDR **`async-pbo-upload` is different**: it polls a three-slot fence queue, copies RGBA32F pixels to CPU using `getBufferSubData`, then `device.queue.writeTexture` uploads them to WebGPU. At W×H this is16WH bytes each direction before other overhead; async avoids waiting for unfinished work but not bandwidth/latency. `float-canvas-external-copy` avoids explicit CPU readback but is not guaranteed zero-copy. Benchmark/report the actual HDR mode separately and never infer scene WebGPU performance from that presenter.

## Why keep Three/WebGL now, and when WebGPU becomes useful

Three is a renderer/toolkit choice; it does not impose the current dense optics algorithm. The local renderer already executes the expensive custom shaders and floating-point ping-pong work on GPU. No evidence here identifies an engine replacement as the smallest repair, or establishes a universally best engine.

The official Three overview describes WebGPURenderer as a different build with node materials/TSL, asynchronous initialization and WebGL2 fallback. Its compute API can express buffer evaluations and reductions. These are capabilities, not a speed guarantee. This live documentation is newer than pinned r180 and is not a compatibility receipt for our vendor build. [WebGPURenderer overview](https://threejs.org/manual/pages/webgpurenderer), [renderer compute/readback API](https://threejs.org/docs/pages/Renderer.html#compute).

Our custom `ShaderMaterial`/`RawShaderMaterial`, vegetation `onBeforeCompile`, GLSL3 MRT, WebGL-specific state/FBO checks, mirror/depth overlays and lens/display stack require an explicit port. ShaderMaterial is WebGLRenderer-only in the official contract; r180's own `Material.onBeforeCompile` comment says the same. WebGL2 fallback on WebGPURenderer does not make incumbent shader hooks compatible. [ShaderMaterial documentation](https://threejs.org/docs/pages/ShaderMaterial.html).

A credible later branch ports **one end-to-end resident path**—density/source buffers → compute → raster → lens/output—rather than assuming a free WebGPU-compute/WebGLTexture bridge. It must account for WGSL precision/order, storage/layout and device limits, readback/query consumers, float renderability, resize/device loss, color/HDR and antialiasing parity. Compute can share tiles and reduce constants, but retains exhaustive pair work unless the algorithm also changes. Migration cannot repair12.55 layers of overdraw by itself.

## Prioritized bounded roadmap

1. **Joint workload accounting, CPU only.** Enumerate main and mirror original row counts, exact reusable light-field identity, physical packet count, map/reduction texels, uploads, raster upper bound and owned bytes at sampled full-life/cumulative phases. Track separate work classes; pair counts alone do not equate tau and SH cost. The current1m cap is per request, not an existing frame governor. If a proposed fresh epoch needs W greater than a newly declared unchanged aggregate budget F, partitioning alone cannot complete it in one frame. No cap raise, native escalation or hidden fallback is admitted.
2. **One exact host-work change at a time.** First propose smoke active-prefix attribute updates and density-revision shared shape packing, or bounded allocation pooling/reuse of already-computed optical rows. Preserve existing row association, bitwise ordinary outputs where unchanged, main/mirror identities and exposure/contact partitions. Test0/1/shrink/regrow/camera move/density revision and stale generation; compare full native image only after CPU tests. Existing per-record optical caches must remain the baseline, not be reintroduced under a new name.
3. **CPU sparse-relevance witness before GPU redesign.** For one captured immutable state, evaluate the full finite-ray reference and a conservative Gaussian-node bound with outward rounding; count traversal plus retained work and cumulative tau/T error. Include narrow gaps, inside smoke, grazing rays, main/mirror, heterogeneous profiles and lifetime/cumulative state. The bound must actually reduce total admitted work including hierarchy construction. Extend independently to SH/lit radiance; SourceT success does not admit lighting or smoke raster approximations.
4. **Tiny exact partition primitive, separately gated.** A16×65 fixture inside existing complete-request capacity can test two original64-packet tile maps plus one final reduction, disjoint writes, unchanged association, once-only exponential, padding, atomic publication/failure, owned memory and full GL state. Chunking lowers maximum draw size, not total exhaustive work. A paused owned-epoch multi-frame job is a different latency contract. Live borrowed arrays/Promise results cannot be inserted into current synchronous `prepare`; that path falls back to CPU. See the peer R24 complete-transmission rebuttal for the narrowed gate.
5. **Then one bounded current-workload profile.** Only after root's explicit gate, measure same camera/quality/HDR mode/exposure/physical state, zero unintended CPU transmission queries, current resolved lighting, CPU stages and asynchronous GPU intervals without double-counting. Separate evolving state, frozen raster and late/cumulative smoke. Record p95/p99 and memory, not just FPS. Daylight water/cloud/hydro/lens experiments come from this attribution, not speculative global quality reductions. Recommended60FPS and advanced roughly30FPS remain user reference targets, not guarantees.
6. **Only if a measured backend limit remains:** budget a separate pinned WebGPU/TSL resident-path prototype. Require output/temporal/HDR/fallback parity and whole-frame benefit after transfers, submission and device-limit costs. Do not combine this with physics, smoke representation and display changes in one patch.

The two peer R24 plans agree on the central correction: exact sharing/culling or independently bounded optical work reduction is needed before over-budget live completeness can fit a strict unchanged total budget. A CPU fallback disappearance, retained old image, dropped source, reduced smoke mass, lower opacity, changed exposure or disabled mirror/lighting is not evidence that the requested full visual workload became faster.

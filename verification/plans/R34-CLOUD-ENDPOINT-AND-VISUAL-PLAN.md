# R34：默认云密度端点、明亮画面及积烟的下一步

R33已修复当前浏览器HDR选屏；海水候选局部一致性与固定计时通过，但没有稳定收益证据，未推广。以下是待执行方案，不代表已有实现或GPU成绩。

1. 从当前sky.js完整 density 函数和独立CPU密度实现提取依赖。在 **uCloudShapeBlend恰为2.0** 时，legacy/thermal的代数权重为0；研究闭合端点分支是否能省去其无用计算。所有小于2的混合保持原有路径；不能改变weather/shape/detail采样、billow/puff/entrainment、base-continuity、coverage/region/moisture、LOD、support或稳定采样偏移。不能顺便减少云形质量。
2. 先做源码/数学反审和可逆变换，独立审查有限值与端点等价域。GPU的mix/FMA舍入可能使直接返回端点与旧表达式不同，代数相等不等于逐位一致；若发现差异先保存原因，不能自动放宽容差。保持CPU对应公式同步等价。
3. 在原有上下文，以真实云形和冻结输入做最小实际shader/附件检查，再决定受控计时。使用明确源码、相机和预算；对一次失败不反复重跑或提高100ms单次/整帧已有门。源码准入、局部像素、单项耗时、整帧FPS、HDR显示和照片感分别判断。旧分段时间含多个系统，不能提前把成本归因于云。
4. 若没有明显收益，保留原实现，转向可证实的瓶颈。此前多发每路约1040万源烟配对仍超过400万完整预算，可能CPU回退/缺失细致受光；需要保持所有源与烟团，而非删暗烟、缩短寿命或减半质量掩盖。
5. 继续明亮烟花原生构图审查：不同层的颜色/亮度/时间、烟云地面海面受光、完整倒影、长期积烟与风扩散。最终视觉依然对照用户真实参考，必要时提供高清图/短片供验收。岸浪能量、水花、水下石子与海平线仍在总目标中。

已认可主爆音效、用户设置和机位必须保留。整个目标 active，不把本计划或局部数值检查当成完成。

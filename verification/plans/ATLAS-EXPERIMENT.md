# Round 2：NASA 4K / 8K 星图离线反证实验

2026-10-26。研究资产与脚本，**没有改运行时、没有把8K装入网页，也没有浏览器GPU性能结论**。

结论先行：**8K有明显帮助，推翻“换高分辨率不会改善亮星”的过强判断；但它仍不是镜头点扩散函数，也不是保通量的4K同图升级。** 8K可以是低风险的作者星图模式候选，不能代替正确星等/PSF的目录混合方案。

## 来源与可复现性

- [NASA SVS4851官方说明](https://svs.gsfc.nasa.gov/4851/)及[官方8K EXR](https://svs.gsfc.nasa.gov/vis/a000000/a004800/a004851/starmap_2020_8k.exr)；官方网页、既有官方JSON元数据、HTTP头和下载hash保存在 `assets/`。8K大小 **130,530,278 bytes**，SHA-256 **`dc6c4f413e85707a29a25a9451148154554ecca2c996f84fa8f47b65ef9ff7c4`**。
- 4K用既有未修改 `assets/night/starmap_2020_4k.exr`，35,997,085 bytes，SHA-256 **`69b841cd048c2ef35543eb1c5819b322530e78aa4b0cab97ec1de3ef56a4ddcd`**。比较EXR源，不把HDR转换误差混入。
- 同批星位置来自[ESA Hipparcos I/239官方CDS服务](https://cdsarc.cds.unistra.fr/viz-bin/cat/I/239)，V<2的小查询保留原始TSV、源/权利元数据及hash。选最亮12条、|dec|<65°、与其他V<2项间隔>.7°；不是挑8K最有利的星。
- Python `OPENCV_IO_ENABLE_OPENEXR=1` + OpenCV单线程成功读两份为float32；源为half-float线性数据。无OpenEXR Python包也未构成解码阻碍。VizieR的Python TLS信任链失败后改用保持证书校验的Windows curl，没有关闭TLS验证。
- 运行 `python verification/plans/celestial-atlas-experiment.py` 重建[数值JSON](atlas-experiment/measurements.json)与图。一次完整解码/测量约3.4s，只是离线脚本耗时。7/7实验完整性检查通过；**这不是7项实时渲染验收**。

## 方法和边界

赤经递增向左、赤纬向上的ERP映射。先在目录位置附近找源峰，再各自求局部亚像素质心；4K/8K对应中心最大相差.05783°，小于一个4K赤道texel。J1991.25目录位置仅用于找星，实际宽度基于各图质心，不用未修自行的坐标强行对齐峰。

FWHM是**线性luma、减局部背景后的双线性重建**水平/垂直中心截面半峰全宽。它包括源绘制核和双线性核，不是测出真实恒星直径、仪器PSF或大气seeing。OpenCV双线性相位有1/32源pixel量化，源的有限采样、邻近暗星和背景估计仍会影响小量差别，不能当亚角秒测光。

通量采用相同.30°角半径孔径，减.35–.50°环的中位背景，并按每行**精确ERP texel立体角** `ΔRA·(sin(dec_top)−sin(dec_bottom))` 积分。它是同一数据的相对角通量比较，不是绝对lux。另做.20/.40°孔径敏感性，不用全图普通像素总和代替球面积分。全景RGB积分不减背景。

24/70mm为1024×640、36×22.5mm画幅的同一针孔投影；分别看Orion/Sirius周围，4K/8K在每个焦段共用相同姿态。共用 `2e-7·2^21=.4194304` 显示增益、Reinhard、精确sRGB；没有逐图自动曝光、锐化、腐蚀、缩星或原图重绘。**离线图不是网页现有ACES/TAA/DOF/PSF链，也没有模拟GPU mip minification。** 因此它能比较源中的大小/背景/通量差异，不能验收网页动态稳定性。

全部12颗的8K角宽都减小。8K/4K FWHM比的中位为 **.713水平/.691垂直**；4K中位约21.27角分，8K约15.55角分。8K更圆、更少方格状双线性轮廓，**不是完全相同的角大小**。

但8K的12–17角分亮核，在70mm、1024px宽时仍约7–10px；4K约10–14px。它依旧是作者绘制的宽亮斑。真实照片中的可见扩展应由镜头、像素、曝光和散射决定，不能把此角宽作为当前相机的固定真实PSF。

.30°亮星孔径的比值中位 **.55675**；.20/.40°敏感性中位 **.63606/.54086**。所以全景约.29的差异不是刚好选.30°孔径产生的。匹配亮星积分约需+.845EV，匹配全景平均约需+1.80EV；**单一全局增益不能同时做到**。不应仅改Loader路径后假设现有星空照度常数和自动曝光标定仍相同。

两源都只有0–1值，且含大量正好1的通道；这12颗的中心像素均为RGB(1,1,1)。这证明这些源的亮核已经在相同峰值饱和，不能把峰值直接作为星等。Sirius/Altair的.30°孔径比仅约1.45/1.55，远小于其V星等对应7.59；有限孔径、RGB与V波段、背景都会影响该数值，**不把它扩大成完整源总光度的精确误差**。可确定的是，图像核本身不提供可直接逆推出相机PSF的无饱和测量。

## 实看图与取舍

已用 `view_image` 实看三幅：

- [相同.7°角域的12颗亮星近裁](atlas-experiment/bright-star-angular-crops.png)：8K轮廓明显更圆，但核与halo仍宽；不是仅把4K截图插值放大后的同一结果。
- [24mm全视图](atlas-experiment/perspective-24mm-comparison.jpg)：8K星点较小、背景更暗，4K银河/细星更亮。不能把更暗误称更接近现场曝光。
- [70mm全视图](atlas-experiment/perspective-70mm-comparison.jpg)：8K有明确细节收益，依旧可辨多个宽圆斑；主问题未被完全解决。

**R3建议分二选一，别把所有方案同时上线：**

1. 如果选择低风险小改，以8K作为明确的“NASA作者atlas”模式，比继续4K更好；重新核其背景/亮星相对标定，接受仍烘焙大星点的限制。额外RGBA16F+mip估算约256MiB，源传输124.5MiB；这不是零成本默认升级，需实际GPU/显存门。不能称完成真实PSF。
2. 若本轮目标必须是随焦段/像素/曝光正确的星点，仍推荐**目录亮星 + 同目录分界的通量守恒暗星/银河层**。本实验支持这个目标，也同时推翻了此前轻视8K收益的依据。官方无Hipparcos/Tycho银河层可以避免盲目去卷积，但完整移除范围要补齐，不能只画少数亮星后漏中间星等。先通过来源、分界、通量、云遮挡、缓存和性能门；拿不到完整数据时回退标明atlas模式，不声称已实现混合。

没有建议整图锐化、统一缩星、强降曝光或给更多随机闪烁。16K是否进一步改善、当前网页实际GPU成本、真镜头PSF及真实相机曝光都**未由本实验验证**。

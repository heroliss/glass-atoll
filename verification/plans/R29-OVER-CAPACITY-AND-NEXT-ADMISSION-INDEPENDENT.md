# R29 requests above 4m and the next complete-work admission

The independent read-only audit `r29-over-capacity-fallback-independent-check.json` passes **4/4**. It combines saved actual-camera CPU provenance/counts, current production policies, zero-context rejection of an over-capacity SourceT request, execution of the exact fallback caller block with a synthetic query counter, and source routing review. It does not replay the physical simulation or evaluate native CPU Gaussian columns, measure a stall, or dispatch GPU work.

At the saved current camera, one event has sampled maxima of **3,226,002 main SourceT pairs, 3,226,002 reflected SourceT pairs, and 3,219,099 SH pairs**. All individual requests fit the current 4m policy; their sum is **9,671,103**, which is a joint workload count, not a single-request limit. Main and reflected source counts happen to match, but their camera keys, ray digests and origins differ: reflection uses the actual per-source mean-water hit. Its T result cannot be borrowed from main. The existing SH surrogate is view independent and needs one fresh bake for the shared world generation.

Two actual accepted launches with seeds 42/43, two seconds apart, reach a saved sampled peak of **3,364 packets, 3,112 main sources, 3,112 mirror sources, and 3,101 emission sources**, before any density merge. This yields **10,468,768 + 10,468,768 + 10,431,764 = 31,369,300 logical pairs**. Each consumer exceeds 4m at 82 of the saved 20 Hz checkpoints. The reports retain real physical merges later at capacity; these counts are not obtained by multiplying the one-event case. These are sampled CPU count witnesses, not a continuous bound or a hardware timing result. Their capture-only successful-transmission metadata is a provider interception, not proof of actual GPU execution.

## What currently happens above the policy

`packSmokeTransmissionInputs` rejects a request above 4m before reading packet geometry, packing, or context access; the production factory publishes no texture. `fireworks.js` then performs a synchronous `medium.writeTransmission` call for each non-smoke ordered source in that view, using the original endpoint and reflection policy. The extracted exact fallback loop invokes 3,112 queries for each of the two views in the synthetic routing test. This is **6,224 full-field query calls**, not a measurement of 20,937,536 dense CPU kernel evaluations.

Each query routes through `pyro-smoke.js` to `pyro-smoke-columns.js`. That existing implementation traverses a 5-sigma BVH, skips nodes/packets only under its cumulative optical omission budget, and tracks actual kernel and traversal counts. Complete-field query semantics do not imply every packet is visited or evaluated. The synchronous UI-thread route creates a plausible latency risk, but its native CPU kernel count and duration have not been measured here. The current fallback is mathematically more complete than using stale T; silently deleting it would change visible attenuation.

SH behaves differently. After packet packing and verification of its group radiance bound, the tiled planner rejects an over-budget complete request before GL. No dense CPU SH bake follows. The volume renderer marks the resolved field ineffective, removes it from the active material, and uses its existing coarse local lighting: up to six shared local sources or two legacy clusters. This avoids a CPU all-pair SH bake but changes lighting detail. R29's fixed numerical gates therefore repair the admitted one-event compute range; they do not establish accumulated-firework performance or equal visual quality above that range.

## Smallest nondegrading next steps

First, measure one **normal fresh scene frame** using real changed physical/emission data, one committed density generation and one current ledger. Record fresh SH `reused:false` and bake-counter delta, actual main and nonzero reflected SourceT prepare/draw counters, and their immediate matching scene draws. Main and mirror may sequentially reuse one SourceT allocation only when each texture is consumed before the next prepare replaces it. A frozen `delta=0` scene with an identical SH cache key does not measure a fresh bake. A fresh compute joint likewise omits volume, water, reflection composition and the rest of the scene. Preserve user settings and keep CPU submission and GPU duration scopes separate.

Then capture complete original two-event current-eye inputs and offline references for a separately calibrated exact larger request. An explicit request ceiling around 11m alone is insufficient: the current **8-map cap** also rejects this geometry. The unchanged generic rectangle decomposition at width 256 and at most 1m conservative 64-slot work per map produces **12 maps + one reduction per consumer** at the saved two-event peak, or **39 numerical draws for three consumers**. SourceT uses 10,555,904 conservative slots per eye; SH uses 10,549,504. The final partial row is a separate rectangle, which is why a naive ceiling of total slots divided by per-map slots undercounts the maps. The initial independent 11-map test assumption is retained as a **3/4 fixture failure** in `baselines/r29-over-capacity-before-map-count-fixture-fix/`; no production policy or shader was changed to make it pass.

A future larger allocation/map policy needs a fresh proof of complete-domain allocation, indexing and old-range compatibility, followed by the actual complete inputs and bounded single-kernel/full-job GPU gates. It must keep every source colour/order/ID and physical packet/mass, and publish only after all maps and reduction succeed. No larger GPU work or production change is authorized by this note. The current 4m/8-map boundary is this validation round's chosen policy, not a permanent user requirement; measured future ceilings may change.

If the complete three-consumer cost remains too large, a sparse candidate list is a separate approximation branch. The existing CPU BVH is a possible source of packet IDs and omitted-optical-depth bounds, with its CPU traversal, packing and per-eye cache invalidation costs included. Main/mirror ray relevance and incoming-light relevance require different queries. Shared physical hierarchy data does not authorize shared T. Any optical omission or aggregate proxy needs an explicit numerical-domain/error gate and all-consumer coherence; no source thinning, stale results, physical mass deletion, or fixed-time visual degradation should be hidden as a performance optimization.

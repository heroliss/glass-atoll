# Next gate: one coherent fresh production scene frame

Design only. No implementation or GPU submission is authorized by this document. First complete the reviewed 5/6/10-draw peak calibration jobs; do not alter their frozen runtime, wrappers or pin records to include a scene render.

## What the current frozen benchmark cannot establish

`benchmarkFrozenSmoke()` sets `qaFrozenWorkload`, forces physical `delta=0` and repeatedly renders the same input. `updateScenePhotometry()` calls `pyroSmoke.prepareLighting()` with the same snapshot object/revision and emission ledger object/version, so the normal SH cache can return `reused:true`. Such a measurement is useful for repeated rendering of a fixed volume, but does not include a fresh density/source generation's complete SH bake each frame. Repeated SourceT calls are still view-specific and must be drawn immediately with their matching sorted row/version metadata.

The selected immutable R29 joint fixture has zero submitted reflection rows. It is not the current camera workload. Motion's separate current-eye CPU witness near +3.90s has 2,301 packets, 1,402 main optical rows, 1,402 reflection optical rows and 1,399 emission-ledger rows: main/mirror SourceT are each 3,226,002 pairs, and shared SH is 3,219,099, for 9,671,103 cross-kernel pairs. Equal main/mirror counts do not imply equal rays, row order or attenuation. Each SourceT request fits 4m, while the aggregate is substantially larger than the ten-draw compute-only job.

Expected numerical work for that eye is **two view-specific SourceT requests, each five maps plus reduction**, and **one shared five-map plus reduction SH request**: eighteen numerical draws before smoke volumes, fireworks, opaque island/water/sky, depth-copy and lens/display work. One SourceT field can retain the normal sequential immediate-consumption behavior; it must prepare reflection T, draw that matching fireworks view, then prepare main T and draw that matching main view. Its borrowed output cannot be saved across the second prepare. The camera-independent SH field is freshly baked once and consumed by both volume views at the same generation, without rebaking it merely because the eye changes.

## Minimal integration seam

Prefer one **new, separate root-owned QA entry** in `main.js` which calls a reviewed verification helper with narrow trusted callbacks. Keep production `frame()`, optical kernels, frozen peak jobs and normal user controls unchanged. The existing `qaRenderLock` must prevent the RAF loop from competing throughout setup, one measured render, timer wait and restoration. Require the healthy paused page, no active benchmark, no diagnostic, no active fireworks/stone gesture and the observed empty user smoke state. Preserve the user's original objects rather than clearing/replacing their saved state irreversibly.

The helper should own one production `createFireworks` instance and one production smoke host, with the same explicitly reviewed QA logical-all profile and 4m/map1m/maps8 configuration. Replay the known causal physical update union on CPU only, with no photometry/render calls during replay; use bounded/yielded chunks under the exclusive renderer lock. Replaying only an approximate timestep sequence is insufficient for claiming the immutable fixture: compare the resulting committed packet/profile data, physical clocks, complete ledger words/groups and material mass against the frozen native phase before the first render. The current camera may then produce different optical rows; those are captured and independently identified, not silently replaced with the old fixture's zero-mirror rows.

Temporarily connect the owned pair to the **same production main callback chain**, replacing only root-owned references and its rig's scene membership for the transaction. Do not construct a lookalike scene or feed precomputed SH textures through a synthetic stub. The narrow root callback should execute one `updateScenePhotometry(0,true)` → `water.render(time)` → `lens.render(scene,focusDistance)` sequence with the owned density, current emissions, current main/mirror cameras and a single `frameSnapshot`. The field has never baked that generation, so `reused:false` and `bakes` incrementing by exactly one are mandatory. Root must audit any auxiliary passes from star-view preparation, local shadows, depth copy, water and lens; they belong to the whole-frame cost and cannot be excluded from a total while still calling it a scene frame.

An alternative public `launchFirework()` + normal RAF + `pauseAtPhysicalTime()` run exercises normal evolution, but renders many unbounded intervening smoke frames and changes the physical update sequence with actual framerate. It is a later evolving-frame test, not the smallest first fresh-frame gate. The controlled CPU replay plus one production render transaction is the narrower first step.

## First image and resource boundary

Start at a reviewed small viewport, such as 160×90 main and proportionate reflection, using an explicit private QA render destination where existing lens/water APIs permit it. Do not silently resize or retain a tiny user canvas. The current lens `setSize()` changes multiple targets, temporal/bloom/upscaler and HDR dimensions; those allocations and any rebuild draw work must be declared and fully restored. If using the existing canvas is the only clean route, save all target/dimension/display/temporal state and make exactly one bounded presentation, then restore the user's original presentation without describing the tiny image as native-resolution acceptance.

The first result is a composed-image correctness and fresh-consumption gate, not full-window performance. Native-resolution volume overdraw remains unknown even when numerical SH/T is fast; two volume renders with thousands of ellipsoids can dominate fragment cost. Record each view's actual volume instances, proxy raster-pixel upper bound, viewport size, resolved field version and the SourceT active row/version/camera key. A small-view gate may justify a separately explicit one-frame native-size gate; it cannot be extrapolated to 60 FPS.

## Observed two-event overbudget route

The additional CPU-only current-eye seed42/43, two-second-spacing study reaches 3,364 committed packets, 3,112 main optical rows, 3,112 reflection rows and3,101 emission rows before any density merge. Each main/mirror request has10,468,768 logical pairs and SH has10,431,764, for31,369,300 cross-kernel pairs. Eighty-two sampled checkpoints exceed4m for at least one kernel. Thus the single-event4m ceiling is not admission of this actual two-event workload.

The current route is not uniformly cheap when that ceiling is crossed. The SourceT pack policy returns unsupported before GPU allocation/submission; `fireworks.fillRecords()` then executes its original CPU fallback query for every retained non-smoke optical row, independently on both eyes. Each query targets the current complete density field but already uses its CPU BVH and finite Gaussian support culling; the logical dense-pair count is not a measured count of CPU candidates or traversals. Returning substantial per-row work to the main thread can still cause a responsiveness cliff; no two-event fallback stall duration was measured here. SH also returns `pair-work-capacity`, but the volume disables the resolved field and uses its pre-existing local/cluster light approximation. That avoids an equivalent all-source SH CPU sum while losing the admitted resolved lighting. The two kernels have different failure behavior; neither is a complete4m solution for repeated fireworks.

A responsive fail-closed guard is preferable to an accidentally unbounded SourceT fallback while a richer QA profile remains unadmitted: compute its complete pair count before entering CPU fallback, and distinguish a small compatible fallback from an overbudget current frame. An overbudget frame can explicitly stop the diagnostic/presentation transaction and preserve the previous presented canvas and responsive controls, reporting that no current result was produced. It must not silently use T1, stale attenuation or incomplete sources. This is a temporary failure containment policy, not fulfillment of unrestricted immediate multi-firework playback, and should not be presented as the final visual solution. It requires its own production review; this design does not change that fallback.

The smallest constructive next numerical step is to capture complete immutable two-event source/SH/current-eye inputs and calibrate them under a separately named larger complete-request policy, retaining1m per map. For these actual counts, complete SourceT partials are3,112×ceil(3,364/64)=164,936 cells and SH partials are3,364×ceil(3,101/64)=164,836 cells. At width256, both use twelve map rectangles plus one reduction: thirteen draws per kernel; two eyes plus shared SH would require39 numerical draws. A proposed12m complete envelope with16 allowed maps would cover these requests without changing the optical kernels or per-map work. Its fixed numerical allocation would be roughly14.6MB for one sequentially reused SourceT field plus shared SH, before QA targets/driver overhead. These are CPU plan/allocation estimates, not hardware admission or timing.

First calibrate one exact complete kernel request and its full independent references on the saved data, with a new explicit whole-job envelope and stop criteria; then calibrate actual joint work before a two-event scene frame. The existing25ms retrospective guard cannot preempt a long synchronous thirteen-draw submission. If measured risk requires per-pass await/guarding for the first calibration, keep all immutable inputs/partial targets owned and publish only the completed reduction. That isolated delayed calibration is not a fast normal-frame solution. Do not claim that dividing dispatches reduces their aggregate work or preserves a60FPS frame by itself.

If complete GPU arithmetic remains the bottleneck after measured calibration, use the actual native snapshots to evaluate a conservative Gaussian hierarchy/spatial relevance bound with certified omitted optical/radiance contribution and joint build/traversal/reduction cost. The earlier synthetic sparse witness is not native proof. Lossy cohort merging, source omission, packet mass deletion, changing smoke lifetime, or WebGPU migration cannot be adopted merely to conceal the current fallback cliff. A future calibrated larger frame budget is possible;4m is an explicit current admission policy, not a permanent user requirement or proof of impossibility.

# R26 follow-on: complete fresh GPU requests beyond the present pair guard

Research only,2026-10-29. No production edit, GPU/browser run or larger native admission is made here. The16×65 three-draw gate is a correctness foundation, **not the live CPU-cliff repair**. The user did not specify a permanent1,048,576-pair limit. That value is the incumbent engineering guard; explicit larger total requests, including roughly4million pairs, can be considered after bounded measurements. The R24 statement that unchanged exhaustive work W cannot fit an unchanged smaller total budget F remains conditional on that chosen F; it is not a prohibition on revising a measured budget.

## Current blockers are distinct

`planSmokeTransmission` in `pyro-smoke-transmission-pack.js` rejects constructor `maxPairs>1048576`, then rejects complete active `count*packets` before packing. Thus increasing only the GPU factory's allocation or splitting its draws cannot admit a larger input. This pair guard is separate from full-SPD/Float32 conditioning gates: original-double world inputs, positive packed factors, whitened-coordinate/direction bounds, finite normalization and raw line bounds must remain intact. Passing those engineering checks is not a universal1e-5 optical-error proof.

`smoke-transmission-layout.js` inherits the same complete-request gate and sizes the compact partial target from it. SourceT's final reduction loops over the original ascending64-packet tiles; packet capacity4096 already implies at most64 tiles. Source rows may number18000. Current physical source and packet caps, texture limits, pixel addressing, upload buffers and complete-source identity are additional limits, not things to remove accidentally with the pair guard.

Resolved illumination is another operator and another cap. `createPyroSmokeLightField` defaults to `maxBakePairs=1048576`; its tiled baker sums64-source SH1 tiles into three RGBA32F attachments. It already shares an exactly reusable density/ledger field between views. Its neutral/zero-field rules, raw bounds, three-attachment work/bytes and signed cancellation differ from finite-ray tau. Raising SourceT alone would leave the lighting-model fallback unresolved.

`fireworks.js` calls synchronous `transmissionBatch.prepare`, validates current count/version/density/camera metadata and draws immediately. Ineffective or thrown output goes through CPU columns. Inserting a Promise, pending status or stale T would preserve or disguise the cliff. Keep the admitted complete GPU route synchronous; asynchronous timer polling belongs to isolated QA, not the live prepare contract.

## Smallest architecture changes after the tiny gate

1. Introduce explicit **complete-request** and **per-map** work limits, instead of overloading one `maxPairs`. Preserve incumbent defaults. A later QA-only configuration can admit a named larger `maxRequestPairs` after its memory/numeric/whole-job proof, while each map rectangle stays within a separately measured `maxMapPairs`. Validate counts and safe products before allocation or source mutation. Do not evade the complete request gate by calling the packer on falsely independent packet slices.
2. Separate packing/numerical validity from the selected total-work policy. A complete input still undergoes all existing original-double/SPD/Float32 checks, keeps every ordered row/mask and packet, and is packed once per view into owned or synchronously borrowed current-generation buffers. The broader total policy is an explicit option with fail-closed defaults, not an unconditional relaxation of `SMOKE_TRANSMISSION_LIMITS`.
3. Size the partial table from the **whole admitted request envelope**, not one chunk. For maximum request budget B and capacities Ns,Np, a conservative logical envelope is `min(Ns*ceil(Np/64), ceil(min(B,Ns*Np)/64)+Ns)`, plus physical end-row padding. At B=4,000,000,Ns=18000,Np=4096, this permits80500 logical texels, rounded to256×315=80640; that partial target is1,290,240 bytes. With the existing packet/source/output textures, one SourceT field's numerical GPU resources would be2,707,456 bytes. This is arithmetic sizing, not measured app VRAM or runtime admission; B=4×1048576 is a different envelope and must not be conflated with4,000,000.
4. Preserve the original shader bodies, uniforms, packet inner-loop order and final tile order. A contiguous owned partial-address interval can be decomposed into an exact first-row tail, zero or more full rows, and a final-row prefix. Up to three nonoverlapping viewport rectangles retain framebuffer-relative `gl_FragCoord`; no extra fragment discard or per-chunk exponential is needed. A rectangle itself can be split further when needed by the per-map budget. Whole-source tile ranges are contiguous; partial-source ranges across multiple tiles are not, unless emitted as separate intervals. Prove coverage/address arithmetic on CPU before dispatch.
5. Submit all maps followed by the single existing reduction in synchronous `prepare`. GPU command order provides map-before-reduce ordering on that context. Keep auto-clear disabled across maps; every required partial cell must be written once before reduction. Publish fresh effective metadata only after the complete validated submission sequence succeeds; any detected context/link/FBO/numeric failure retires it. No current-source or current-camera result may be relabeled from an older generation. Live code cannot await a per-map timer; preflight work/memory limits plus prior QA measurements are its prospective guard, while QA can stop the *next* submission after an observed slow/faulted draw.

R26's fixed16×65 rectangles are only the same-row special case of this interval decomposition. General decomposition, allocation and admission require their own tests and gate; the tiny result does not authorize a count/cap jump by itself.

## Three-consumer frame accounting and output lifetime

Build a coherent whole-frame request summary before starting newly admitted larger work: main finite-ray T, reflected finite-ray T, and one resolved field when its exact density/ledger key is not reusable. Keep separate counts/cost classes for pairs, conservative64-slot work, reduction texture reads, rectangular fragments, upload bytes, draws, owned memory and smoke raster fill. Sum measured weighted costs; a tau pair, SH1 source moment and blended smoke pixel are not equal operations.

Main/reflected origins differ and their ordered optical rows are not the current emission ledger. Do not share T merely by source ID or count. The current SourceT output is borrowed and replaced by the next prepare. Two safe synchronous designs are (a) preflight/reserve the complete frame, then prepare-and-immediately-draw each view in command order, or (b) keep separate owned output slots per required view. Preparing both views first into one shared output and drawing later would overwrite one view. Preflight must also preserve or privately capture reused FW ray/ledger buffers; a view-preparation pass cannot borrow the same mutable array for both views.

This can require a small CPU separation between optical-row/view-request preparation and final draw, with existing physical/shutter/contact caches reused. It does not require making the whole renderer asynchronous. Coherent input time stays fixed across a frame and all source-provider queries remain causal. A GPU-result failure before all required content is admitted needs an explicit whole-request/frame policy; silently dropping mirror, resolved light or smoke does not satisfy the desired feature.

The present755×1734 SourceT witness needs1,309,170 pairs. That is a sensible **separately gated frozen complete-request** follow-on before a later roughly4million single-consumer lifetime witness, rather than treating one tiny pass as approval for every endpoint. Native main/mirror/illumination together can be substantially larger than any one request. Their actual row counts must be measured; three times a resolved-ledger count is only a sizing illustration. Larger requests can be fast enough, but that is a hypothesis to measure, not ruled out or assumed true.

# 烟花历史边界采样缓存

2026-10-27。此次只改 `fireworks.js` 的 `getBounds()` 与其私有 WeakMap；未改变风时序、粒子、渲染、声音或摄影预算。基线是 `892dd94713a82b27da414e723e10197444a7f4ead1ce1b4bcd6c6319ea397d74`，完整源保存在[基线目录](baselines/fireworks-before-past-bounds/sha256.json)。当前冻结源 SHA256：`606d57528ec7c28e36d56734746a00826ef03272aea86ff5e42f6bff29486abf`。

每个 body 仍采样原来的 `birth + life*j/16` 共17点。仅在 `birth <= t <= simulation.time` 时保存已算过的位置；未来点每次缺失原完整边界缓存时仍执行原 `sampleBody`。完整缓存 key、2Hz时间桶、当前风失效规则、样本顺序、8m余量、烟包络与最终并集运算均未改变。

爆点与分裂父粒子的初态在未来风改变后可能变化，因此缓存比较初始位置/速度的数值、birth/life/drag/gravity、父粒子身份及版本、速度增量。任何实际改变均清空该 body 的17点缓存，子粒子递归继承父版本。尚未出生的 body 不建位置缓存。WeakMap 不强持有离场 body；没有新增跨事件的强引用列表。

## 正确性

```powershell

```

- 恒风与1.4s平滑变风，分别按30/60/120Hz输入。
- 分裂十字、扇形、垂柳、棕榈的出生前预报、爆开/分裂、燃尽、事件移除；另覆盖后续发射与风段裁剪。
- 主体数值初态、drag/gravity/birth/life及分裂父体/速度增量改变后的失效。
- 后续风改变时，过去位置复用，未来每一调用与旧实现逐一同序；原完整key的同状态对象缓存仍保留。

共比较 **1,635组完整边界**，最大绝对差 **5.6843×10⁻¹⁴m**。不是新的轨迹近似：缓存与重新求值仅出现解析表达式/风前缀重组的浮点舍入量级差异。对照实际记录了 **3,017,655次未来采样**，调用顺序与参数完全一致；减少 **2,132,114次已过去的采样重算**。测试的容差为1e−10m，实际误差单独披露。

[匹配CPU窗口](fireworks/past-bounds-benchmark.json)另有508组边界，min/max逐值差为0。原[物理回归](fireworks/physics-check.json) **22/22**、[音频回归](fireworks/audio-check.json) **12/12**通过。物理与风前缀源哈希未变。

本轮也重跑了[标量投影回归](fireworks/scalar-bound-check.json)，更新范围守卫后 **7/7**：12,491个数值对照的误差、低估、可见性变化均为0。第七项旧守卫曾断言“getBounds源码不变”，因这次明确授权的优化而失败；[旧失败原报](fireworks/scalar-bound-pre-past-scope-failure.json)已先保存。新守卫保留shader/fillRecords原文本比较，并以892dd冻结源检查除getBounds及其私有WeakMap外的每一字节（包含projection/getRadianceBound）；新16/16报告的源哈希也必须匹配当前文件，不接受陈旧通过。最终606源在真实浏览器重载后，实际GPU预算夹具再次 **7/7**，见[最终源首次运行记录的bound字段](fireworks/past-bounds-runtime-first.json)。

## CPU测量

仅Node CPU，不含GPU提交/上传或整场渲染帧率。两朵菊、8段尾迹、相同种子、完整record、主/镜像相机预算，先预热20帧；30/60/120Hz各48个测量帧。144Hz复现原审计：先317个风节点，再80个测量帧，3492条record、最终417个风段。此次整个基准9.83s。

表中为 `getBounds` 耗时，单位ms，列为平均 / p95 / 最大值；包括原key命中返回，不强行让恒风每帧重算。

| 输入 | 旧实现 | 历史缓存 |
|---|---:|---:|
| 30Hz 恒风 | 0.140 / 1.293 / 3.235 | 0.104 / 1.252 / 1.549 |
| 60Hz 恒风 | 0.070 / 0.020 / 1.430 | 0.089 / 0.068 / 2.262 |
| 120Hz 恒风 | 0.048 / 0.020 / 1.866 | 0.037 / 0.022 / 1.127 |
| 30Hz 变风 | 5.185 / 6.724 / 7.180 | 2.262 / 3.231 / 3.480 |
| 60Hz 变风 | 4.729 / 6.743 / 8.106 | 3.002 / 4.252 / 4.255 |
| 120Hz 变风 | 3.994 / 5.191 / 6.393 | 4.032 / 5.751 / 6.280 |
| 144Hz 原审计变风 | 4.589 / 5.884 / 6.771 | 2.045 / 2.760 / 3.307 |

144Hz目标窗口平均下降约55%；同一窗口整个CPU组合均值11.722→9.603ms、光度阶段7.168→4.713ms。30/60Hz变风均改善，但120Hz这轮未改善；恒风原本多数命中2Hz缓存，数十微秒的均值不作稳健收益。前后窗口顺序运行，共享CPU与JIT/GC会带来波动，不能把所有阶段差异都归因为缓存，也不据此声称浏览器FPS提升或每帧达60。

执行入口：

```powershell

```

未来样本、当前风变化后的完整边界更新和原有保守余量仍全部保留，因此出生前预报仍可能较贵。此次按授权范围在这里冻结，不再调整边界刷新频率或删减风节点。

## 最终606源的真实浏览器压力窗口

主代理随后重载同一冻结源，在实际1209×1292、中档、原生HDR、月光岛屿、两朵菊的完整渲染循环中，将风从1.8调到5m/s，保留1.4s平滑和完整风节点。保留[首轮记录](fireworks/past-bounds-runtime-first.json)、[暖机重复](fireworks/past-bounds-runtime-warm.json)及[暖机严格窗口汇总](fireworks/past-bounds-runtime-summary.json)，不只挑较快一轮。

| 实际窗口 | 首轮约4.025s | 暖机重复约4.022s |
|---|---:|---:|
| 平均场景FPS | 27.33 | 41.03 |
| 帧间隔数量 / CPU阶段样本 | 110 / 111 | 165 / 166 |
| 帧间隔p95 | 59.70ms | 37.10ms |
| GPU平均 | 22.12ms | 15.89ms |
| 光度CPU平均 | 6.56ms | 4.27ms |
| 烟花更新/声音调度CPU平均 | 13.03ms | 8.93ms |
| 主渲染/镜头/显示CPU平均 | 6.93ms | 4.88ms |

阶段均值仅取benchmark开始至结束的严格窗口，未把较长profile中的空闲帧混入。渲染间隔数与CPU提交样本数相差一帧，不能把166个CPU样本写成166个独立帧间隔。GPU计时与CPU提交有重叠，不应将两者简单相加为帧时间。

两轮高record取样帧及末帧的opaque/composed/reflection整张RGB归约均为 **NaN=0、Inf=0、负有限分量=0**，分类器为`ieee-bits-v2`。暖机高record帧为3488条，P后线性RGB最大值：opaque77.6875、composed72.5、reflection310.75；这些是特定源种子、观察角度和时刻的存储数值，不是显示nit或所有帧的最大值证明。

冷暖差异明显，且两轮并非完全相同事件种子与峰值可见性，**不能把27.33→41.03FPS当作这次缓存的因果收益**。首轮低于30FPS，暖机也未达60；本机此中档重负载不保证每帧30或60，更不代表手机/其它设备。此次能确认的是最终源的真实GPU预算回归仍通过、所检帧数值有限，以及Node匹配场景下历史重算减少；全场性能仍受烟花更新、反射/云与显示路径等共同限制。

缓存的适用前提仍是生产风时序只追加/裁剪、既有风段不原地改写。主体/父体的实际初态或参数改变已有版本失效；若将来增加重写旧风历史或时间倒退的编辑功能，还需显式使这份历史缓存失效，不能只清风响应缓存。

# R31 fixed native CPU preplan

`captureR31CurrentViews(THREE, pair, {camera, reflectionCamera, frame, optics, viewExtents})` is a new verification-only function in `r31-native-preplan.js`. The root supplies the actual main/reflection cameras and resolved production target sizes. `viewExtents` is exactly `{main:{width:1209,height:1292}, reflection:{width:1209,height:1292}}`; both inner objects have only own enumerable data fields. Unknown dimensions, extra/accessor fields, an omitted extent or non-native main optics reject. The original camera aspect stays1209/1292. This is one closed native gate, not an arbitrary-size public renderer API.

The caller must supply a trusted complete causal replay pair. The fixed phase retains2301 packets,1399 light-ledger rows,1420 physical records and density time163/revision4785, with32 empty plus633 active updates. The function verifies actual host snapshot values against the owned pair, freshness before any smoke rendering/SH request, and unchanged columns/physical generation both before and after asynchronous digests. It invokes the actual production firework CPU projection with inert render/batch acknowledgements, owns every original binary64 endpoint/origin and active flag before the first await, including private copies of frame/optics/resolved target metadata, then freezes the returned data. It does not call a real renderer/context, attenuation query, SH bake or numerical optical oracle.

Return shape remains `{views,lightPlan,receipt}`. Each `views` entry has `kind`, complete `count`, `width`, `height`, `viewExtent`, `inputOwned`, `captureMetadata`, `rayDigest`, `sourceTPlan` and origin diagnostics. `inputOwned` retains the R30 schema: full original-double endpoint/origin arrays, full active mask, eye, request version, density revision and camera key. `sourceTPlan` contains the unchanged pure complete `layout`, exact `rectangles`, submission flag and numerical draw count. The receipt adds `resolvedViewExtents`, native main optics, original camera aspect and the explicit CPU/inert-only scope. Fake acknowledgement labels never count as GPU evidence; the actual scene must prepare/consume fresh real fields before the corresponding draws.

The actual unmodified **Node-exact** production replay is used for this CLI proof. It is deliberately not called a browser-reference positive replay: Node and browser binary64 physical expectations remain distinct, while the physical recipe is the same. The immutable post-restoration user inventory supplies the actual scale1 native target dimensions, camera/lens state and reflection matrix. No synthetic scene, altered producer or precomputed source physics is substituted.

CPU acceptance is6/6 in `r31-native-preplan-check.json`:

- Both native views retain all1402 active rows; main has one eye origin and reflection has1402 actual mean-water intersections.
- Each SourceT request remains3,226,002 logical pairs and5 exact maps+1 reduction; shared SH remains3,219,099 pairs and5 maps+1 reduction. All3 complete requests total9,671,103 distinct-kernel pairs and18 numerical draws, within4m/request and1m/map/eight-map limits.
- A **next actual production FW fill** receives real `Float64Array` endpoints/origins and `Uint8Array` active data. Every original row equals the frozen preplan. Packing those actual typed inputs into full65536-word packet and216064-word source buffers is bit-identical to packing the owned view; all199240 unused source words remain zero. No short/maxSources-only buffer is accepted as the padded texture layout.
- Request versions advance1/2→3/4 in the CLI's main-then-reflection fill order. Optical `recordsGeneration=667` is compared to its captured optical namespace; current luminous-ledger `recordGeneration=1` remains separate. The actual browser frame may use reflection-first request order and must validate that actual sequence independently.
- Caller-local optics/frame/extent mutations during digest do not change the owned view or receipt; the original6cca source/5-check result is retained under `baselines/r31-before-metadata-owning/`.
- A disposed pair during digest cannot publish a preplan, and wrong/missing/accessor extents reject before another fill. Full physical snapshot, material, ledger identity and column diagnostics remain unchanged.

`r31-native-preplan-admission.json` retains all original rays, per-eye metadata/plans, shared SH plan, exact target inventory provenance and complete next-fill upload hashes. Its input is CPU evidence, not a precomputed GPU result. The root's actual browser pair/preplan must reconstruct and validate its own native rays; no cross-engine ray equality or native image/time/FPS claim is made here.

# R38 检查点：未使用汇总的候选没有获得稳定收益

**本轮没有推广性能改动。** 去掉两处完整快门窗口中无人消费的汇总计算，数值等价通过；完整首次消费者的 CPU 收益小且阶段间相反，因此候选已归档、生产逐字恢复。整体目标仍为 **active**，照片感、持续性能与多发积烟尚未完成。

## 候选与决定

新增 taps-only writer，只输出原有八个 RGB bin，保留所有运算次序、24项独占缓冲、旧完整公开 API、部分接触路径、物理、shader、烟量和光强。候选层模块 `411ebd75…d948715`、FW `3f1093fa…0004605`。writer 自检7/7、独立5/5、实际 FW 完整行/两眼上传 CPU 对照5/5，模式与恢复独立审查4/4。它们证明候选输出与合同，不证明性能收益。

writer 隔离调用约为旧汇总调用的0.81倍，但完整 CPU flow 的324条旧版/新summary/新taps样本并不支持稳定推广：

| --- | ---: | ---: | ---: |
| +0.7 s | 10.2640 ms | 9.9531 ms | 0.9697 |
| +1.7 s | 11.8211 ms | 12.0472 ms | 1.0191 |

目标 +1.7 秒点的均值及中位数都稍慢；所有样本与原版单独一臂保留，未通过挑选阶段或删除离群值制造收益。结果含 Node/V8/JIT/GC/调度影响，**没有执行 native A/B，没有新增GPU候选任务，也不宣称整帧提速**。

候选与依赖/脚本/结果共134项封存于 [归档清单](baselines/r38-rejected-taps-writer/manifest.json)。生产112个源码指纹全部恢复R37，main仍 `08b43c65…0cbedf`、FW `03fdb703…d45c735`、layer `41124296…78c537`；已认可主爆音效 `4e5ede41…b8ec31` 保持。浏览器未加载候选，无需重载。

## 额外定位，没有顺带改算法

[只读光学构建归因](r39-optical-construction-attribution.json)在原03fd工厂做了一次有界54例CPU诊断，三个阶段完整行与物理/接触结果保持一致。+1.7 秒首次构建有1728次RGB窗口、1728次真实过去锚点采样（1536尾部+192头部）、4800次锚点缓存请求、1728次接触支持检查及3456次曝光对象调用；镜像已命中共享光学行，无新的RGB或姿态采样。

带计时的嵌套段在该阶段约为RGB窗口2.73ms、锚点/姿态3.40ms、接触0.77ms、投影0.39ms，其余混合记录工作约2.95ms。计时侵入开销明显（计时版比只计数版约多1.83ms），不能当作native8.33ms的精确分账，残差也不是纯分配/GC。现有 `getRadianceBound` 已包在 `withWindResponseMemo` 内；“光学姿态未使用wind memo”的猜想经源码检查否决，不重复添加缓存。逐代扁平行缓存只列为后续候选，尚未实现或声称收益。

下一步优先处理 [多发密烟GPU方案](plans/R39-DENSE-GPU-READONLY-PLAN.md) 中明确的回退条件。现有GPU已有分块，4m请求门/8map容量与三个消费者的总工作是独立限制。旧双发证据每眼约10.47m配对、SH约10.43m，总31.37m；扩大容量本身不减少这些运算、体积填充或CPU准备。先捕一个当前真实双发CPU快照并核算主/镜/SH共同工作量，再做有界数值/整帧校准；不会直接提高日常上限，也不会用旧SH/T配新场景。
